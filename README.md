# Моё решение для поиска объявлений

На каждый запрос я отдаю 50 объявлений из `benchmark_items.parquet`. Готовый файл — `answer.csv`. Его создаёт `final_solution.py`; все нужные части поиска и локальные веса смысловой модели лежат рядом с кодом. Данные в архив с кодом не включены: проверяющий может взять исходные три Parquet-файла из задания.

## Как повторить ответ

Нужны Python 3.12+ и около 32 ГБ оперативной памяти. Положите `train.parquet`, `benchmark_queries.parquet` и `benchmark_items.parquet` в папку `data/`, затем запустите из корня проекта:

```bash
python -m pip install -r requirements.txt
python final_solution.py --data data --output answer.csv
python check_answer.py --answer answer.csv --data data
```

Веса смысловой модели уже находятся в `models/semantic_minilm/`. Интернет для запуска не нужен. При первом запуске код создаст в `data/semantic_experiment/` кеш векторов заголовков, поэтому он будет дольше повторного. Фиксированы разбиение, случайное зерно и 350 деревьев LightGBM. SHA-256 готового `answer.csv`: `164d974a27b1daeee16bd0a169a6b54f76dfc28dc2c9ab3d2b869d3575a7db8c`.

## Что использовал

Из корпуса объявлений беру заголовок, описание, параметры, категорию и подкатегорию, город, координаты, цену, рейтинг и число отзывов. Из запросов — текст, город, категорию, фильтры и признак доставки. `train.parquet` даёт примеры выбранных объявлений, историю выборов по похожим запросам и статистику подходящих подкатегорий. Это помогает не сводить поиск только к буквальному совпадению текста.

Сначала собираю кандидатов по словам заголовка, символьным частям слов, описанию с параметрами, истории похожих запросов и смысловой близости запроса к заголовку. Для текстового и смыслового поиска беру кандидатов как по всему корпусу, так и внутри локации запроса. Смысловые векторы считает локальная модель `paraphrase-multilingual-MiniLM-L12-v2`.

Затем `LightGBM Ranker` ранжирует общий пул и выбирает 50 объявлений. Он видит оценки разных способов поиска, относительное место кандидата, совпадения слов и фильтров, расстояние, подкатегорию, цену и признаки объявления. Смысловая модель помогает найти и оценить объявления с другой формулировкой; LightGBM учитывает вместе с ней условия запроса.

Что пробовал и как вышло

- **Текстовый поиск.** Начал с поиска по словам заголовка, частям слов и короткому описанию. LightGBM выбирал из кандидатов 50 объявлений. Recall@50 на старом control был **0,8073**.
- **Больше текста объявления.** Удлинил описание и параметры, затем добавил признаки совпадения запроса с описанием. Recall@50 на control вырос сначала до **0,8211**, потом до **0,8353**. Это помогло объявлениям, где услуга указана только в описании.
- **История и подкатегории.** Добавил объявления из истории выборов по похожим запросам и признаки подходящей подкатегории. На control получилось **0,8525**. Дополнительный поиск по локальной истории пользы не дал.
- **Настройка ранжировщика.** 350 деревьев LightGBM подняли control до **0,8555**. Проверял XGBoost, классификатор, другую функцию ранжирования и обучение на большем числе запросов — убедительного выигрыша не получил.
- **Optuna.** В отдельном опыте подбирал параметры LightGBM. После переобучения вариант дал **0,8542** на старом control против **0,8525** у тогдашней базы. Прибавка маленькая; в итоговый ответ Optuna-модель не вошла.
- **Смысловой поиск.** Сначала добавил его оценку как признак — control вырос до **0,8613**. Затем стал брать дополнительные объявления по смысловой близости заголовка и запроса. Получилось **0,8662**, охват кандидатов — **0,9497**. Это итоговый вариант в `answer.csv`.
- **Сложные примеры.** Жёсткий отбор снизил dev Recall@50 до **0,8021**. Более аккуратная смесь сложных и случайных примеров на новых разбиениях дала **0,8436** против **0,8352** базы, но улучшение не повторилось на каждом разбиении.
- **Cross-encoder.** Самостоятельно он дал **0,5434** на новых разбиениях. Как дополнительный признак LightGBM — **0,8427** против **0,8352** основной базы, но результат тоже был неустойчивым, а расчёт занимал около **2,75 секунды на запрос**. Его в ответ не добавлял.
- **Настройка под топ-50 и разбор ошибок.** Проверил отсечение обучения и число деревьев: **0,8369** против **0,8352** на новых разбиениях, с ухудшением на одном из них. Среди известных положительных объявлений 41 осталось на местах 51–200, ещё 52 не попали в пул кандидатов.

**Итог:** у отправляемого решения Recall@50 **0,8922 на dev** и **0,8662 на старом control**. Эти наборы уже просматривались, скрытая оценка неизвестна. Поздние опыты проведены на другой копии проекта и другом разбиении, поэтому их цифры нельзя напрямую сравнивать с итоговыми **0,8662**. Файл для сдачи проверен: 2452 запроса, ровно 50 разных объявлений на каждый; повторный запуск создал побайтно тот же `answer.csv`.

## Как проверял

Для локальной проверки использовал строки `train`, где выбранное объявление есть в корпусе бенчмарка. Одинаковые тексты запросов разделял целиком: 10 000 контекстов для обучения, 1000 для настройки и 1000 для контроля. Основная метрика — средний Recall@50 по контекстам. На dev получилось **0,8922**, на control — **0,8662**; охват кандидатов на control — **0,9497**. Control уже просматривался в ходе разработки, поэтому это исследовательская оценка. Оценка скрытого теста мне неизвестна.

Перед сдачей проверил CSV по исходным `query_id` и `item_id`: в файле 2452 запроса, ровно по 50 разных объявлений на каждый, идентификаторы без изменения регистра и все встречаются в корпусе. Проверка находится в `check_answer.py`. Повторно запустил `final_solution.py` в отдельный файл: он побайтно совпал с отправляемым `answer.csv`, включая SHA-256.

## Какие ошибки встретились

- Поиск по целым словам пропускал объявления из-за окончаний и опечаток. Добавил поиск по символьным частям слов.
- У части объявлений услуга написана в описании, а не в заголовке. Увеличил используемый фрагмент описания и добавил два признака совпадения с ним.
- Запрос и объявление иногда описывают одну услугу разными словами. Добавил смысловой поиск по заголовкам и его оценки в ранжирование.
- Среди текстуально похожих объявлений важны город, расстояние, фильтры и подкатегория. Передал их LightGBM отдельными признаками.
- История выборов могла подсказать ответ для точно такого же обучающего запроса. При обучении исключаю собственный текст запроса из истории и статистики; проверочные тексты исключаю целиком.

Отдельно пробовал cross-encoder и выборку сложных примеров на другой исследовательской копии. Устойчивого выигрыша они не показали, поэтому в этот ответ их не добавлял.

Пожалуйста, открывайте `answer.csv` как текстовый CSV. Excel может испортить строковые идентификаторы.
